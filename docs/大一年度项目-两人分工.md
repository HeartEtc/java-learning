# 大一年度项目：两人分工方案

> 制定：2026-10-09
> 成员 A：Java 侧（负责数据处理与统计计算）
> 成员 B：R 语言侧（负责可视化与统计分析）
> 项目：数据驱动的机场调度优化（见 `大一年度项目-需求与设计.md`）

---

## 1. 分工原则

**核心原则：只在一处计算，把算好的结果交给对方画图。**

🚫 **绝对不要"两边各算一遍"** —— 你的程序和同学的 R 脚本算出的数字必须完全一致。如果两边都实现统计逻辑，报告里出现两个不同的"平均延误"，**答辩时这是致命的**。

---

## 2. 成员 A（Java 侧）负责什么

**范围：从原始数据到"聚合后的统计结果"**

| # | 任务 | 产出 |
|---|---|---|
| 1 | 读入原始 CSV | `List<Flight>` |
| 2 | 数据清洗（丢缺失、丢非法时间） | 清洗日志（丢了多少条、为什么） |
| 3 | **按小时分组统计**：航班数、平均延误、延误率 | `hourly_stats.csv` |
| 4 | **按航线分组统计**：Top N 延误航线 | `route_stats.csv` |
| 5 | 航班级明细（用于 R 画散点图/分布图） | `flights_clean.csv` |
| 6 | 调整规则的生成与应用 | `hourly_stats_adjusted.csv` 等 |
| 7 | 前后对比表的数值 | 对比 CSV |

**技术路线（与 Java 学习路线重合）**：
- 第一版：`ArrayList` + `HashMap` 手写循环（W3 集合）
- 第二版：接 IO，读真文件、写 CSV（W4）
- 第三版：用 `Stream` 的 `groupingBy` 重写统计（W6）

---

## 3. 成员 B（R 语言侧）负责什么

**范围：从"聚合好的 CSV"到"图表与统计结论"**

| # | 任务 | 产出 |
|---|---|---|
| 1 | 读 `hourly_stats.csv` / `route_stats.csv` | R data.frame |
| 2 | **高峰时段可视化**：每小时航班量柱状图 + 平均延误折线（双轴） | 图 1 |
| 3 | **延误分布图**：直方图 / 箱线图（按航线或时段分组） | 图 2 |
| 4 | **Top 延误航线**：横向条形图 | 图 3 |
| 5 | **调整前后对比图**：分组柱状图 | 图 4 |
| 6 | R 侧的统计补充（相关分析、趋势描述、显著性检验等） | 分析结论 |
| 7 | 图表美化、统一配色与字体、导出高分辨率 PNG | 报告用图 |

**注意**：R 侧**不做数据清洗**，也不从原始数据重新算统计量 —— 只消费 A 产出的聚合结果。

## 4. 接口：CSV 格式约定（**这是两个人的合同**）

**现在就把列名固定下来，谁都不许随意改。要改必须提前说。**

### `flights_clean.csv`（航班级明细，供 R 画分布图）

| 列名 | 类型 | 示例 | 说明 |
|---|---|---|---|
| `date` | `YYYY-MM-DD` | `2026-03-15` | 日期 |
| `flight_no` | 字符串 | `CA1234` | 航班号 |
| `route` | 字符串 | `PEK-SHA` | 航线（起降机场三字码） |
| `sched_dep_hour` | 整数 0-23 | `8` | **计划起飞小时**（分组用的关键列） |
| `delay_minutes` | 整数 | `23` | 延误分钟（负数表示提前） |
| `is_delayed` | 0/1 | `1` | 是否延误（>15 分钟记 1） |

### `hourly_stats.csv`（按小时聚合）

| 列名 | 类型 | 示例 |
|---|---|---|
| `hour` | 整数 0-23 | `8` |
| `flight_count` | 整数 | `142` |
| `avg_delay` | 小数（1 位） | `18.4` |
| `delay_rate` | 小数（3 位） | `0.317` |

### `route_stats.csv`（按航线聚合）

| 列名 | 类型 | 示例 |
|---|---|---|
| `route` | 字符串 | `PEK-SHA` |
| `flight_count` | 整数 | `96` |
| `avg_delay` | 小数（1 位） | `25.7` |
| `delay_rate` | 小数（3 位） | `0.412` |

### 对比文件

同一份结构，加一列区分即可：

| 列名 | 值 |
|---|---|
| `scenario` | `original` / `adjusted` |

其余列与 `hourly_stats.csv` 相同。

**格式硬要求**：
- **UTF-8 编码，不带 BOM**（否则 R 里读出来首列名会多出乱码字符）
- 第一行是列名，逗号分隔，**不要有空格**
- 缺值用**空字段**表示（不要写 `NULL` / `-` / `NA`）

## 5. 关键：**并行开工**（别互相等）

**不用等真数据，也不用等对方写完。**

1. **A 先造一份假数据**：20~50 行 `flights_clean.csv`，字段齐全、故意混入几行缺失值
2. **A 把它 `git push` 到仓库**
3. **B 立刻能开始写 R 绘图脚本** —— 因为格式已经定死了
4. 等真数据到位，A 只需要换 `loadFromCsv` 的文件名和字段映射，**B 的 R 代码一行都不用改**

**这就是"先把接口定下来"的价值**：两个人的开发完全解耦。

---

## 6. 协作方式

| 项 | 建议 |
|---|---|
| 仓库 | 用现成的 `java-learning`，把同学加成 collaborator；或在 GitHub 新建一个专用仓库 |
| 目录结构 | `src/com/example/flight/`（Java）、`r/`（R 脚本）、`data/raw/`（**不进 Git**）、`data/output/`（聚合结果，**进 Git**）、`docs/`、`report/` |
| 大文件 | 原始数据可能几十 MB，**不要提交进 Git**。在仓库里放一份 100 行的样例文件即可 |
| 沟通 | 每天在群里同步一句"今天产出了什么文件"；**改 CSV 格式必须提前说** |
| 分工声明 | 报告和答辩里写清楚：**A 负责数据处理与 Java 程序实现，B 负责可视化与统计分析** |

---

## 7. 三个最容易出问题的地方

| 风险 | 后果 | 预防 |
|---|---|---|
| **两边各算一遍统计** | 报告里数字对不上，答辩崩 | **统计只在 Java 侧做**，R 只画图 |
| **CSV 格式被单方面改动** | 对方的脚本全部报错，白干一天 | 格式写进本文档，改前先沟通 |
| **只有一个人干活** | 老师会看出来；另一个人答辩答不上 | 每人**必须能讲清自己那半边**，也要能讲清对方那半边在干什么 |

## 8. 汇报节奏

| 时间 | 各自产出 |
|---|---|
| 10-11（周日） | A：造好假数据并 push；B：读完 R 的绘图基础 |
| 10 月中下 | A：第一版统计跑通；B：用假数据画出 3 张图 |
| 11 月上 | A：接真数据 + 导出 CSV；B：换成真数据出图 |
| 11 月下 | 合起来做调整前后对比；A 用 Stream 重写统计 |
| 12 月 | 一起写报告、做 PPT |

## 9. 答辩时要能回答的问题（两人都要准备）

1. **数据清洗丢了多少条？判定标准是什么？**
2. **"高峰时段"的定义是什么？**（必须给出明确标准，不能含糊）
3. **调整前后对比，指标改善了多少？如果没有改善，为什么？**
4. **你们用了什么工具链？为什么这么分工？**（"我们用 CSV 作为两边的接口，避免重复计算"——这是加分答案）
