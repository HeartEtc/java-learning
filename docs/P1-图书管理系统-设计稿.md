## 2. 字段设计

### Book
| 字段 | 类型 | 说明 |
|---|---|---|
| `isbn` | `String` | 国际标准书号。**用 String 不用 int**：13 位超出 int 上限（2,147,483,647），且保留前导零、可含 `X` |
| `title` | `String` | 书名 |
| `author` | `String` | 作者 |
| `id` | `String` | **系统内部主键**（如 `B001`），借阅记录用它关联 |
| `available` | `boolean` | 是否可借 |

> **简化声明**：一个 `Book` = 一种书，`available` 只表示有没有。
> **更严谨的模型**：一种书对应多个副本，每个副本是一个 `Book` 对象、共享同一 `isbn`，字段用 `int availableCopies`。
> P1 第一版采用简化模型，将来重构。

### User（抽象类）
| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | `String` | `private final` |
| `name` | `String` | `private final` |

### Loan
| 字段 | 类型 | 说明 |
|---|---|---|
| `book` | `Book` | 借的书 |
| `user` | `User` | 借书的人 |
| `borrowDate` | `LocalDate` | 借出日期 |
| `dueDate` | `LocalDate` | 应还日期 |

### Library
| 字段 | 类型 | 说明 |
|---|---|---|

| `bookCount` / `userCount` / `loanCount` | `int` | 三个计数器（`count` 语义同 `Bank`：下一个空位下标） |

## 3. 关键设计决策

| 决策 | 结论 | 理由 |
|---|---|---|
| `User` 做抽象类还是普通类？ | **抽象类** | 系统里不该存在"普通的用户"，必须是读者或管理员之一。跟 `Account` 一样的思路 |
| 抽象方法放什么？ | **`getRoleName()`** | 唯一能在两个子类间产生真实差异、代码量又极小的方法。`User.toString()` 靠它体现多态，**父类零 `instanceof`** |
| 权限怎么表达？ | **`instanceof` 判断** | `if (user instanceof Admin)` 才允许加书。**第一版就这么写**；更正规的做法是权限字段或独立权限枚举 |
| "书已被借走"怎么表达？ | **返回 `boolean`** | 这是"正常但少见的结果"，不是编程错误。异常留给"不该发生的情况"（如书 ID 不存在） |
| 书 ID 不存在怎么表达？ | **抛异常** | `BookNotFoundException`。调用方传了一个系统里没有的 ID，属于传参错误 |
| 自定义异常继承谁？ | **`RuntimeException`** | 非受检：不强制每个调用方 `try-catch`。ID 不存在是"编程错误"，快速失败更好 |
| 时间用什么？ | **`java.time.LocalDate`** | 不用老的 `Date` / `Calendar`（已过时） |
| `Loan` 的日期怎么定？ | **由 `borrowDate` + 期限算出** | 保留双日期构造器 + `!borrowDate.isBefore(dueDate)` 校验作为兜底 |
| 数据容器用什么？ | **数组** | 还没学集合。**接受"容量写死"的限制**，在注释标注 W5 重写 |
| 借还逻辑放哪？ | **`Library` 的方法** | `Library.borrowBook()` / `returnBook()`。`Loan` 只存数据，不写动词方法 |
| 计数字段是实例还是 `static`？ | **实例字段** | `Library` 的 `bookCount`/`userCount`/`loanCount` 属于**某一家图书馆**；只有 `Loan.totalLoans`（全系统累计创建记录数）才用 `static` |
| `Book` 构造器参数顺序 | **`(id, isbn, title, author)`** | `id` 和 `isbn` 同为 `String`，**主键放第一位靠位置区分**。曾因顺序不一致导致"数据明明加了却查不到" |

## 4. 已决定的事项

> **09-20：不加独立 `id` 字段，用 `isbn` 当业务主键 + 另设 `id` 作为系统主键。**
> 实际实现保留了 `id`（形如 `B001`）作为系统主键，`isbn` 作为业务字段。
> 理由：借阅记录按 `id` 关联更稳；`isbn` 将来在"同书多副本"模型下会重复。

- [x] 权限检查放 `Library`（`Main` 不出现业务判断）
- [x] 数组容量在构造器传入（`new Library(10, 10, 10)`），演示用 10
- [ ] 借阅记录的"超期"要不要算？**P1 不做**，P2 再做日期统计
- [x] `addBook` 遇到重复 ID 该不该拒绝？**结论：拒绝并返回 `false`，且必须在任何写操作之前返回**（`containsKey` 判断 → `return false` → 才 `put`）。理由：重复添加是"调用方用错 API"，属于可预期的正常分支，不是异常情况
- [x] `borrowBook` 成功时要做哪几件事、失败要不要回滚？**结论：不需要显式回滚，改为"先判完所有条件再动状态"**。顺序固定为：找书 → 找人 → 查可借 → 查限额 → 改 available → 加 borrowCount → 建 Loan。任何一步失败都在改状态之前 `return false`

### 测试写法上的三条铁律（这次踩出来的）

1. **每段测试新建 `Library`**，不要共用一个实例——否则前一组的状态污染后一组。
2. **任何一段崩溃 = 后面全不跑**。修 `Book.equals` 之前有一组因 `UserNotFoundException` 崩溃，第 6～10 组全部没执行。以后每组单独 `try/catch`（学 JUnit 后由框架隔离）。
3. **测"拒绝"必须同时断言"状态没变"**。只断言返回 `false` 是不够的——`withdraw(2000)` 那次返回 `false` 的同时把余额改成了 `-500.0`。成对写：`返回值 + 状态快照`。

## 7. 实施中踩到的坑（供 README / 面试用）

| 坑 | 现象 | 根因 | 对策 |
|---|---|---|---|
| `Book` 参数顺序不一致 | `findBookById("B001")` 抛异常，但书明明加进去了 | 构造器声明 `(isbn, id, ...)`，调用方按 `(id, isbn, ...)` 传；**两个都是 `String`，编译器不报错** | 主键放第一位；开启 IDEA 的 `Parameter Names` 提示 |
| `users[bookCount] = user` | 恰好没暴露（两个计数相等），换顺序就出错 | 下标用错了变量 | 数组与计数一一对应，写的时候念一遍变量名 |
| `id.equals(book.getId())` | 传 `null` 时抛 `NullPointerException` 而非业务异常 | `equals` 用在了可能为 `null` 的一方 | 用"确定非 null"的一方调 `equals`，或 `Objects.equals` |
| `Library` 计数字段加 `static` | 两个 `Library` 实例共享计数，新建一个会清零另一个 | 把"对象的属性"误当"类的属性" | 判据：每个对象各自一份 → 实例字段 |
